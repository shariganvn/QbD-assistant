# Phase 1: Typed evidence, complete inventory and safe fact-card bindings

## Context links

- Gate: `gates.yaml` → G-01.
- Input: Phase 0 matrix, cell receipts and result inventory.
- Existing contracts: `cowork-p2-kit/reasoning/fact-cards.schema.json`,
  `cohort-evidence.mjs`, and `contracts.mjs`.

## Overview

Convert Phase 0 outputs into one exact three-formula evidence package. Enforce
specification, observed result, and composition context as machine-validated
types. Derive record roles from the complete source inventory so a caller cannot
hide an adverse result by omitting it or relabeling it as context.

## Requirements

- Typed evidence kinds:
  - `specification` — operator, threshold(s), basis and provenance;
  - `observed_result` — numeric value/statistic/unit/candidate and provenance;
  - `composition_context` — croscarmellose sodium level/candidate/provenance.
- Fact cards used for scoring must bind to exactly one `observed_result` ID.
  Specification IDs are structurally forbidden from scoring-card bindings.
- Composition fact cards may support rationale only; evaluator must not score
  them unless a future approved rubric explicitly adds that measure.
- Candidate set must equal formula-01/02/03, not merely contain one or more IDs.
- `result-inventory.json` is derived from the complete Phase 0 cell-receipt set.
  Every inventory item must be admitted, excluded with an error-coded reason, or
  represented by an observed-result binding.
- `recordRoles` is generated by the validator from evidence kind and inventory.
  The caller cannot supply or override roles.
- Package binds source DOCX hash, store hash, cell-receipt-set hash and evidence
  envelope hash.

## Architecture

```text
Phase 0 receipts + inventory
  -> validate evidence-kind schema
  -> exact candidate-set guard
  -> inventory reconciliation
  -> derive recordRoles
  -> create v1-compatible fact cards
  -> create mandatory fact-card-to-evidence bindings
  -> emit one sealed real-data package
```

The existing fact-card v1 schema stays unchanged for compatibility. Structural
spec/result safety lives in a mandatory formulation evidence envelope and
binding validator consumed by the formulation evaluator. A producer cannot
bypass the guard by directly constructing a v1 fact card because the evaluator
rejects a missing or wrong-kind binding.

## Implementation steps

1. Write failing tests for spec-as-result, missing formula, duplicated formula,
   omitted inventory record, role downgrade, and ambiguous receipt binding.
2. Implement evidence envelope validation with exact keys and evidence kinds.
3. Build observed-result records for dissolution min/mean/max, assay and CU AV.
4. Build specification evidence for dissolution, assay range and strict CU `<15`.
5. Build composition context for croscarmellose 1%/3%/5%.
6. Reconcile every inventory record and derive roles; reject caller-supplied roles.
7. Produce fact cards plus binding map; scoring cards may reference only
   `observed_result`.
8. Hash and emit the complete data package; prove deterministic bytes.

## Success criteria

- [x] G-01 passes (evidence under `docs/reports/qbd-p221-formulation-selection/`).
- [x] Candidate set equals the exact expected three IDs (`E_EXACT_COHORT` guard).
- [x] Spec-as-result fails even when the caller bypasses the normal constructor
      (`E_SPEC_AS_RESULT`, tested on a directly-constructed card).
- [x] Omitted or downgraded adverse records fail inventory reconciliation
      (`E_INVENTORY_RECONCILIATION`, `E_ROLE_OVERRIDE`).
- [x] 1%/3%/5% composition claims have source-bound context evidence.
- [x] Package hashes bind source/store/receipts/evidence/fact-card mappings
      (`formulation-data-package.json` + `hashes.json`).

## Risk assessment

- A local guard alone is bypassable → evaluator requires validated evidence and
  binding artifacts as mandatory inputs.
- Record inventory may over-classify context as results → derive from Phase 0
  cell receipt types and require explicit error-coded exclusions.
- Extra composition cards could accidentally enter scoring → evaluator accepts
  only rubric measure IDs and observed-result binding kinds.

## Security considerations

- No caller authority over `recordRoles`.
- Reject duplicate IDs, duplicate candidate/measure/statistic bindings, unknown
  evidence kinds, and cross-source hash mixing.
